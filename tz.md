Кратко: это ТЗ описывает функциональные и нефункциональные требования, данные, рабочие шаги и критерии приёмки для системы автоматического сбора, обогащения, верификации и дедупликации подрядчиков по инженерным сетям. Нейросеть получает этот документ как «источник правды» — здесь описаны что должно получиться, формат данных, правила объединения/решений и критерии качества. Код и архитектуру нейросеть проектирует сама, исходя из требований ниже.

4. Функциональные требования (что должно быть реализовано)

4.1 Общая логика
	1.	Еженедельный запуск пайплайна, создающего/обновляющего записи в БД.
	2.	Для каждой найденной карточки собирать исходные поля (см. 4.2).
	3.	Параллельно: обогащение официальными проверками (если есть ИНН/ОГРН/ФИО) и целевым поиском отзывов на дополнительных площадках.
	4.	Дедупликация по правилам (раздел 6).
	5.	Для итоговой карточки генерировать AI-суммаризацию отзывов и уровень риска.
	6.	Экспорты/API/ручная очередь — для оператора.

4.2 Обязательные поля карточки (формат и типы)
	•	id — canonical id (string/uuid).
	•	source_records — массив (source, source_id, source_link, collected_at).
	•	name_raw — исходное название (string).
	•	name_normalized — нормализованное название (string).
	•	type — enum: ЮЛ / ИП / ФЛ / unknown.
	•	inn / ogrn — string / null.
	•	phones — массив телефонов в E.164 или строка с оригиналом + normalized.
	•	emails — массив.
	•	addresses — массив структур {raw, region, district, city, street, geo}.
	•	contacts_json — JSONB со всеми контактами (включая соцсети, whatsapp, сайты).
	•	average_rating — float (агрегат по всем источникам).
	•	reviews_count — int.
	•	reviews_sample — массив (up to N) объектов {text, date, rating, author, source_link}.
	•	summary_review — текст AI (ограничение 200–400 слов).
	•	risk_level — enum green/yellow/red.
	•	risk_reasons — array JSON объектов {reason, evidence_link, severity}.
	•	merged_sources — array с перечислением источников после дедупа.
	•	last_updated — timestamp.

4.3 Таблицы (минимум)

5. Пайплайн — этапы и требования к результату (строго по этапам)

Этап 1 — первичный сбор (collector)
	•	Источники: используем перечисленные источники (раздел 2). Где есть API — использовать API. Где нет — целевой сбор только карточек найденных кандидатов (не full-site crawl).
	•	Хранить исходный payload (raw JSON/HTML snapshot) для каждой записи.
	•	Для каждой записи: извлечь поля из 4.2 и записать в companies_raw_omsk и связанные reviews_raw_omsk.

Требование к качеству: каждая запись должна иметь как минимум одно контактное поле (телефон или сайт) и ссылку на источник.

Этап 2 — обогащение (enrichment)
	•	Нормализация телефонов (E.164), адресов (разбор на поля), привязка к региону/району.
	•	Целевой поиск отзывов на дополн. площадках (VK, Flamp, Otzovik, Google) — только по кандидату (name + city + phone).
	•	Если в карточке обнаружен ИНН/ОГРН/ФИО → запуск проверок по официальным реестрам (см. секцию «проверки»). Результат сохранять в checks JSONB.
	•	Пометка confidence score для каждого enrichment (0–100).

Требование к качеству: для каждой enriched-записи confidence >= threshold (например, 70) или запись идет в ручную очередь.

Этап 3 — дедупликация и нормализация
	•	Нормализация имён: убрать юридические формы (ООО, ИП и т.д.), привести к нижнему регистру, убрать кавычки/пунктуацию, транслитерацию учесть.
	•	Правила слияния:
	•	Если совпадает inn → merge (автоматически).
	•	Иначе рассчитывать composite score:
	•	name_sim (rapidfuzz token_sort_ratio) weight = 0.6;
	•	phone_match (бинарно) weight = 0.3;
	•	region_match weight = 0.1.
	•	composite = 0.6name_sim + 0.3(phone_match?100:0) + 0.1*(region_match?100:0).
	•	merge если composite >= 85; помечать «вероятный дубликат» если composite ∈ [70,85); иначе — разные.
	•	После слияния строить canonical карточку и сохранять список исходных источников в merged_sources.

Этап 4 — AI-суммаризация и оценка риска
	•	На вход: выборка отзывов (up to 200, релевантные).
	•	На выход: summary_review (структурированный текст — краткое резюме, 3 сильных стороны, 3 слабых стороны, тенденции за последние 12 мес.) и risk_reasons (не более 5 причин с ссылками).
	•	Формирование risk_level: правило-движок (пример):
	•	red — найдено банкротство/исков/исполнительные листы, активные ограничения/дисквалификации;
	•	yellow — отдельные негативные кейсы + спорные отзывы, неоднозначная история;
	•	green — нет значимых признаков риска.
	•	AI-сводка должна указывать ссылки на доказательства (по возможности — source_link).

Требование к качеству: в выборке sample 200 карточек ручная оценка отображает адекватность summary > 85%.

Этап 5 — финальная база и обновления
	•	Результат записывать в companies_omsk_clean.
	•	План обновления: еженедельно — новые записи + обновление отзывов, критических проверок.
	•	Добавление новых компаний: если карточка не совпала с существующими правилами дедупа — создать новую запись.

6. Проверки подрядчика (автоматические / полуавтоматические) — что проверять

(реализовать автоматические адаптеры к каноническим реестрам; остальные случаи — полуавтоматический targeted search)

Обязательные автоматические проверки (при наличии ИНН/ОГРН/ФИО):
	•	Наличие/статус в налоговом реестре (ЕГРЮЛ/ЕГРИП).
	•	Наличие исполнительных производств (ФССП).
	•	Наличие арбитражных дел/решений.
	•	Наличие в реестре банкротств (ЕФРСБ).
	•	Наличие подрядов/участий в госзакупках (ЕИС).
	•	Наличие в реестре НОСТРОЙ (если применимо).

Fallback (если ИНН нет или автоматика не дала результат):
	•	Целевой поиск по name+city на Google / 2GIS / VK / Flamp / Otzovik — получить ссылки и краткие метрики (кол-во отзывов, оценки).
	•	Если confidence проверок < threshold — пометить для ручной проверки.

Формат результата проверки: checks JSONB, каждая запись: {checker_name, status (found/not_found), details, evidence_link, checked_at}.

7. API контракт (минимум, без реализации кода)
	•	GET /companies?region=&risk=&min_rating=&service= → возвращает список объектов с ключевыми полями (id, name_normalized, average_rating, risk_level, contacts_json, last_updated).
	•	GET /companies/{id} → возвращает полную карточку (включая reviews_sample, checks, merged_sources).
	•	POST /companies/{id}/manual_review → принимает результат ручной проверки и обновляет карточку.
	•	GET /exports?format=csv&filter=... → экспорт итоговой таблицы.

Форматы полей — JSON. Для телефонов — E.164 в normalized поле, оригинал сохранять в raw поле.

8. Нефункциональные требования
	•	Хранение: PostgreSQL (JSONB для гибких полей).
	•	Частота обновлений: еженедельно.
	•	Производительность: полный еженедельный прогон должен завершаться в пределах ресурсов сервера (параметризуемо); система должна поддерживать horizontal scaling адаптеров.
	•	Надёжность: ретраи для внешних запросов, запись snapshot raw payload для аудита.
	•	Логирование: подробные логи адаптеров + метрики (collected_count, enriched_count, merged_count, manual_queue_size).
	•	Безопасность: все ключи/секреты хранятся в защищённом хранилище, доступ по ролям.
	•	Бэкапы БД — daily snapshot + WAL retention.
